The Dilemma

클라우드 관제 센터의 고민

"지금 접속해 온 로봇이 정말 해킹당하지 않았는가?"

원격지 공장에서 구동 중인 휴머노이드 로봇이 클라우드에 연결할 때,
단순한 아이디/비밀번호나 파일 인증서로는 신뢰할 수 없음:

  • 해커가 탈취한 인증서로 가짜 로봇 행세를 하며 허위 텔레메트리 전송 가능
  • 로봇 OS 내부에 백도어가 돌아가고 있어도 겉으로는 정상 통신인 척 위장 가능
Runtime Measurement

Linux IMA (실행 측정 아키텍처)

커널 서브시스템인 IMA(Integrity Measurement Architecture)가
execve() 시스템 콜을 인터셉트하여 모든 실행 바이너리의 SHA-256 해시를 측정함. 

User -> execve(/usr/bin/actuator_node)
           |
           +-> Linux IMA 서브시스템이 바이너리 데이터 읽음
           +-> SHA-256 해시 계산
           +-> /sys/kernel/security/ima/ascii_runtime_measurements 기록
           +-> fTPM PCR 10 하드웨어 레지스터로 Extend 호출!
TCG Protocol

도전-응답 (Challenge-Response) 증명

  1. 클라우드: 32바이트 일회용 난수(Nonce) 챌린지 전송
  2. 로봇 fTPM: Secure World 내부에서 PCR 10과 Nonce를 묶어 증명키(AK)로 서명 (TPM2_Quote)
  3. 로봇: Quote 서명 번들과 IMA 측정 로그를 클라우드로 전송
  4. 클라우드 검증:
    • Nonce가 일치하는가? (재전송 공격 차단)
    • IMA 로그 재생 결과가 fTPM 서명 PCR 10과 일치하는가?
    • 골든 베이스라인과 일치하면 [TRUSTED: 제어권 부여]
Network Security

단방향 TLS vs 상호 mTLS

일반 단방향 HTTPS

클라이언트만 서버를 검증함.
서버는 클라이언트의 실제 하드웨어 신원을 암호학적으로 확인할 수 없음.

상호 mTLS (우리 플랫폼)

서버와 로봇 클라이언트가 서로의 X.509 인증서와 하드웨어 서명을 상호 검증.
인가된 정품 로봇만 통신망 입장 허용!

Zero Plaintext Key

Secure World 연동 mTLS 1.3

로봇의 클라이언트 비밀키는 파일시스템에 저장되지 않고,
ARM TrustZone OP-TEE Secure SRAM에 봉인되어 있음: 

OpenSSL 3.x Client  --1. TLS 서명 필요 (CertificateVerify)-->  pkcs11-provider
                                                                     |
OP-TEE PKCS#11 TA   <--2. SMC 호출 (C_Sign, Secure SRAM 키)---------+
                    --3. 하드웨어 내부에서 ECDSA 서명 생성
OpenSSL 3.x Client  <--4. 결과 서명값만 수신 (비밀키 노출 0%)---------+

서버와 통신하는 동안 비밀키는 단 1비트도 메모리에 노출되지 않음!

Key Takeaway

핵심 요약

  • 제로 트러스트: 원격지 로봇을 무조건 신뢰하지 않고 매 접속마다 검증
  • IMA + PCR 10: 실행된 모든 코드의 해시를 하드웨어에 누적 기록
  • Nonce 챌린지: 일회용 난수로 과거 정상 상태 Quote의 재전송 공격 차단
  • Secure World mTLS: 개인키 노출 없이 TrustZone 내부 서명으로 양방향 TLS 1.3 수립
