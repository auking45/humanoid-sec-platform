Security Foundations 03

리눅스 커널 하드닝

해커는 왜 링 0를 노리는가?

Ring 3 vs Ring 0 • KSPP 메모리 하드닝 • 모듈 서명 강제 • unprivileged eBPF 차단

Privilege Levels

CPU 권한 계층 구조

Ring 3 / EL0 (User Space)

ROS 2 제어 노드, Python 스크립트, 웹 애플리케이션 (제한된 메모리, 하드웨어 접근 불가)

⬇️ 시스템 콜 (System Call) 경계 ⬇️

Ring 0 / EL1 (Kernel Space)

리눅스 커널, 하드웨어 드라이버 (모든 물리 메모리, CPU 레지스터, 모터 액추에이터 통제)

Threat Analysis

링 0 권한 장악 시의 치명적 위협

  • 물리적 로봇 오작동: 모터 토크 및 속도 제한 파라미터를 메모리에서 직접 덮어써 안전사고 유발
  • 완벽한 은닉 루트킷: ps, ls 도구에서 악성 프로세스를 감쪽같이 숨김
  • 보안 소프트웨어 무력화: SELinux, 방화벽, 감사 로그를 실시간으로 메모리에서 0으로 패치

👉 따라서 커널 자체가 스스로를 방어하는 KSPP(Kernel Self-Protection) 필수!

Memory Hardening

물리 메모리 직접 접근 차단

과거 리눅스는 루트 계정이 /dev/mem 특수 파일을 열어
전체 물리 RAM을 임의로 읽고 쓰는 런타임 커널 패칭이 가능했음! 

# 우리 플랫폼의 KSPP 커널 설정
CONFIG_STRICT_DEVMEM=y
CONFIG_IO_STRICT_DEVMEM=y

✅ 루트 사용자라도 시스템 RAM 영역 접근 시 하드웨어 에러(EPERM) 반환!

Integrity Gate

커널 모듈 서명 강제

리눅스 커널은 런타임에 드라이버 모듈(.ko)을 로드할 수 있음:

CONFIG_MODULE_SIG=y
CONFIG_MODULE_SIG_FORCE=y
CONFIG_MODULE_SIG_ALL=y
CONFIG_MODULE_SIG_SHA256=y
  • 모든 .ko 파일 끝에 PKCS#7 디지털 서명 강제
  • 서명이 없거나 1바이트라도 변조된 루트킷 모듈은 커널이 즉각 적재 거부(ENOEXEC)
  • 서명 개인키는 SoftHSMv2 토큰 내부에 봉인되어 공격자 위조 원천 차단
Attack Surface Reduction

비인가(Unprivileged) eBPF 차단

eBPF는 커널 내부에서 바이트코드를 실행하는 고성능 기술이지만,
Spectre 취약점 및 메모리 유출 공격의 핵심 통로로 악용됨. 

CONFIG_BPF_UNPRIV_DEFAULT_OFF=y
# 런타임 sysctl 파라미터 강제
sysctl -w kernel.unprivileged_bpf_disabled=1

일반 사용자 계정에서 eBPF 명령 호출 시 커널이 즉각 차단!

Key Takeaway

핵심 요약

  • Ring 0 방어: 커널이 뚫리면 소프트웨어 방어는 무력화되므로 KSPP 필수
  • 메모리 격리: CONFIG_STRICT_DEVMEM으로 /dev/mem 메모리 패칭 차단
  • 모듈 서명 강제: CONFIG_MODULE_SIG_FORCE로 미서명 루트킷 100% 거절
  • eBPF 통제: 비인가 eBPF 차단으로 사이드채널 및 권한 상승 통로 봉쇄
